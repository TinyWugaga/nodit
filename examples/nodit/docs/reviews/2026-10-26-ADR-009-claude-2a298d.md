## Findings

- [x] **P2（實作前）重建 ADR 的驗收應依新內容重新判定。** 0009:86 寫「重新建立後回到原本的狀態」，與 :73–75 的 hash 規則不完全一致。例如原本 current 的 ADR 被刪除，再以相同 ID、不同內容建立，應為 stale，不能回到 current。建議改成「重建後依新 blob 與 adr_rev 重新計算」，驗收分成相同內容恢復 current、不同內容變 stale、沒有紀錄維持 unrecorded；不保留或還原刪除前的派生狀態。 已處理：驗收改為重建後依新 blob 重新計算，分 current／stale／unrecorded 三種情況，並註明不保留或還原先前的派生狀態。

- [x] **P2（實作前）補定無效／重複 ADR 的解析政策。** 0009:72–83 只定義存在與 hash 比對，並要求模式照 linkReviews；但 `core/review.ts` 的 linkReviews 對同 ID 只取第一筆，未排除有 error 的卡片，`server/project.ts` 的 retainCard 又會保留解析失敗前的卡片。因此照搬可能在 ID 重複時依掃描次序顯示 current 或 stale；解析失敗時則可能依是否保留舊卡片而顯示 stale 或 missing。推薦新增 `invalid` 派生狀態，表示目標無法唯一且有效地解析，優先於 hash 比對，顯示「ADR 無法判定」，並沿用原有診斷說明原因。至少覆蓋重複 ID、目標解析失敗及修復後重新判定；不要從候選檔任取一份，也不要拿保留的舊 card 推斷 ADR 已 accepted。這是前次第 3 項未完全收斂的邊界，不需要擴張為新的工作流程。 已處理：新增 invalid 狀態（ID 重複、解析失敗含 retainCard 保留的 card），判定優先於 hash 比對、彙總順序最高；spec-adr-not-accepted 遇 invalid 不判斷；驗收含修復後重新判定；並註明 linkReviews 改用同一個共用解析函式。
